# M6 — Agents: co-pilot, scene naming, resident interviews

**Goal:** the "agentic" half of the pitch.
- **Co-pilot:** a tool-calling LLM that can:
  - read the city;
  - run *what-if* scenarios on forked futures without touching the live city;
  - change the live city when asked;
  - ask Qloo about tastes;
  - explain the results with numbers and real names.
- **Scene naming:** a cheap LLM call names each scene from its real Qloo tags and artists.
- **Resident interviews:** chat with a resident who speaks only from their own taste and history.

**Decisions:** [0003](../../decisions/0003-llm-provider-agnostic-deepseek.md): Vercel AI SDK, DeepSeek primary, free-tier fallbacks. The AI SDK is v7 (`ai@7.0.122` and matching `@ai-sdk/*`, pinned to releases at least two weeks old).

|---|---|---|---|
| DeepSeek | `DEEPSEEK_API_KEY` | `deepseek-v4-flash` (thinking off) | `deepseek-v4-flash` |
| Groq | `GROQ_API_KEY` | `openai/gpt-oss-120b` | `llama-3.1-8b-instant` |
| Cerebras (OpenAI-compatible) | `CEREBRAS_API_KEY` | `gpt-oss-120b` | `gpt-oss-120b` |
| OpenRouter (OpenAI-compatible) | `OPENROUTER_API_KEY` | `deepseek/deepseek-v4-flash` | same |
| Gemini | `GOOGLE_GENERATIVE_AI_API_KEY` | `gemini-3.5-flash` | `gemini-3.5-flash-lite` |

- Only providers with keys join the chain. Every model ID can be overridden with `<PROVIDER>_MODEL` / `<PROVIDER>_SMALL_MODEL`, because model lists change.
- `fallbackModel(models)` wraps the chain as one language model. If a provider fails *before streaming anything* (429, 5xx, network or auth error), it tries the next one.
- With no keys, the routes answer 503 and the UI shows "co-pilot offline; the toolbar still works".

## Co-pilot

- **Route `POST /api/copilot`:**
  - `streamText` with `stopWhen: isStepCount(8)` and capped output tokens;
  - a per-IP token bucket (in memory);
  - a system prompt with the city, the week and the rules (below).
- **Server tools** (Qloo, through the cached `src/qloo` client with a budget floor):
  - `qloo_search(name, type)`: finds entities in Qloo;
  - `qloo_taste(names…)`: tag affinities for an entity, to explain what a taste "means".
- **Client tools,** run in the browser against the worker via `onToolCall` and `addToolOutput`:
  - `city_summary`: week, residents, venue counts, fidelity, scenes (id, size, top tags and artists), recent events and actions.
  - `find(query, kind?)`: venues, artists, tags and areas in this city matching a name, with IDs.
  - `venue(id)`: kind, area, open, health, tonight's visitors, its crowd's scenes.
  - `scene(id)`: size, top entities, home areas, venues it goes to, lineage.
  - `what_if(actions, weeks)`: runs the actions on a fork *and* a no-action baseline fork for N weeks (max 26). It returns per-scene size changes, venues closed and opened, the biggest visit winners and losers, new fans of an event's headliner, and fidelity. The live city is untouched.
  - `apply(actions)`: changes the live city, only when the user asks. The UI shows a toast, a camera fly-to and the effects.
- **Actions** the model can name, mapped to the existing action schema:
  - `close_venue(venue)`
  - `open_venue(place, area)`
  - `throw_event(artist, area, weeks?)`
  - `rent_pressure(area, magnitude)`
  - `migrate(count, area, like_scene)`

  "Area" is a venue ID or a cell, resolved to a cell in the browser.
- **System prompt rules:**
  - always use a `what_if` with a baseline before claiming an effect;
  - quote numbers from tools;
  - name real places and artists only when a tool returned them;
  - say when an effect is small or noisy;
  - never apply a change the user didn't ask for.
- **UI:**
  - a collapsible co-pilot panel, with message parts rendered (text, plus compact tool chips such as "Ran a 12-week what-if…");
  - suggested prompts;
  - clicking a venue or scene name in an answer flies the camera there.

## Scene naming

- **Route `POST /api/name-scenes`:** takes the scenes' top tags and artists and uses `generateText` with `Output.object` to return `{ id, name, latin }` per scene. Examples: "Velvet-rope clubbers" and *Clubbus mayfairensis*.
- **Caching:**
  - client-side by lineage ID;
  - a new lineage is named when it first appears, in batches;
  - the legend falls back to "Scene N" plus its top entities.

## Resident interviews

- **Route `POST /api/interview`:** streamed chat. The persona context is built in the browser:
  - the resident's top tastes, with names;
  - home area, scene, venues visited recently, and tastes picked up recently.
- The system prompt keeps the persona to its taste: it never invents favourites outside the given list, and speaks first-person and casually.
- **UI:** "Talk to a resident" in a scene's legend row, which picks a typical member and opens a chat drawer.
